## 二、最重要的发现：角色外观从未进入提示词

### 现象

第一次真实跑图，我给出的角色设定是：

```
林晚：黑色短发齐耳，深蓝地铁制服左胸工牌，银色细链耳钉
```

**生成结果：长发、黑色大衣、白色高领毛衣、星星项链——完全不是这个人。**

### 排查过程（四层丢弃，每层单独看都无害）

我逐层打点，最后定位到**四个独立的丢弃点**串成一条链：

| 层 | 问题 | 后果 |
|---|---|---|
| 1 | `shotsFromTree()` 返回**嵌套镜头**，而 `characters` 声明在**场景**上 | 演员表为空 |
| 2 | `characterById` 把 id/name 映射成**姓名字符串**，不是角色卡 | 即使查到也拿不到外观 |
| 3 | `list()` 这个辅助函数**故意把对象压成 `.name`**，丢光其他字段 | 外观在进入提示词前就被丢掉 |
| 4 | `buildShotRef()` 只输出**姓名** | 提示词里根本没有外观 |

**净效果**：每条分镜提示词都在说

> 「画面中的 **林晚** 必须严格沿用其角色设定三视图：面部、发型、体型身高、服装与配饰逐项一致」

——却**从未描述过林晚长什么样**。模型被命令去对齐一份它从未见过的设定。

**命名不等于描述。** 这是整个 bug 的本质。

### 修复

1. `shotsFromTree()` 让镜头**继承场景的演员表**（镜头级演员表仍然优先）。
2. `characterById` / `sceneById` 映射到**完整卡片**，并同时接受 id 与 name 两种键。
3. `buildShotRef()` 改为逐个输出角色卡里的**真实外观字段**，不再走 `list()`。
4. 未知角色**诚实降级**为「与设定集保持一致」，而不是假装有描述。

### 修复前 vs 修复后（同一提示词、同一模型）

| | 修复前 | 修复后 |
|---|---|---|
| 发型 | 长卷发 | **黑色齐耳短发** ✅ |
| 服装 | 黑色大衣+白高领 | **深蓝地铁制服** ✅ |
| 配饰 | 星星项链 | **银色细链耳钉** ✅ |
| 工牌 | 无 | **左胸工牌** ✅ |
| 场景 | 泛化车厢 | **地铁车厢（对应设定）** ✅ |

**并且这是纯文本达成的一致性**——该渠道只支持文生图，**没有传参考图**。

## 三、第二个真实缺陷：场景光照从未进入提示词

镜头里的 `sceneId` 由剧本 slug 派生（`scene-subway-night`），
而设定集里的场景 id 是 `scene-subway`。

**这两个 id 永远不可能相等**，所以 `sceneById[sceneId]` 永远查不到，
场景主图的光照、构图**全部丢失**。

修复：场景查找增加**按名称回退**（`scene` / `location`），
并给 `sceneById` 同时建立 name 别名。

## 四、上游的真实状况（必须如实说明）

### 这是一个**不稳定**的上游

我做了受控测量：

| 结果 | 耗时 | 含义 |
|---|---|---|
| 成功 | **28–54 秒** | 源站在超时前返回 |
| 失败 | **125.2 秒**（几乎精确） | **HTTP 524**，Cloudflare 源站超时 |

实测成功率在不同时段从 **1/4 波动到 4/4**，**与时段关系很大**。

### 我一度误判，这里更正

我曾怀疑是 `User-Agent` 缺失导致失败，并做了 A/B 测试：

```
不用 UA: 1/4 成功
使用 UA: 2/4 成功
```

**这个差异没有统计意义，我的假设是错的。** 真正的原因是**耗时**：
成功都在 ~30 秒，失败都卡在 125 秒被 Cloudflare 掐断。
**不是请求格式问题，是上游生成太慢。**

### 插件的处理是正确的

遇到 524 的那一批，批量生成返回：

```
返回 ok=true  生成 3 张  失败 1 项
```

**阶段没有崩，失败被逐项归因，可以直接重试。** 这是正确的降级行为。
真实脚本对 524 自动重试——某一批里分镜图重试 3 次后成功。

最后一批 **4/4 全成功**，说明上游恢复后流水线完全通畅。

## 六、新增回归测试

**`docs/verify-character-lock.mjs`（22 条断言，全绿）**

专门防这次的 bug 复发。它**穿过真实路由处理器**验证整条链：

- 角色卡的**头发/服装/配饰**必须真的出现在分镜提示词里
- 提示词**不得**退回到通用兜底句（那说明演员表又空了）
- 场景主图必须带上场景光照
- 纯姓名仍可用，但**不得伪造描述**
- 只有 `title` / 只有 `id` 的卡片都不能被丢掉
- 静态检查：`buildShotRef` 不得再用 `list(v.characters)`（**含正向对照**，
  证明这个检测器对旧写法确实会报警）

**为什么这条链的单测全都过了、问题却还在**：每一层的单测都只测自己，
而数据是在**层与层之间**丢掉的。所以这个套件刻意断言**端到端**。

## 八、仍然没有验证的（如实列出）

1. **参考图 / 图生图**：该渠道只支持文生图，**没有传过参考图**。
   本次一致性**完全靠文本锁**达成——这既是好消息（说明文本锁有效），
   也是限制（说明参考图通路仍未验证）。
2. **视频阶段**：没有配置视频渠道，第 6 阶段只产出提示词包；
   本次运行「产出 0 个提示词包」（脚本没有可转的视频单元），**未真正验证**。
3. **跨镜一致性只测了 2 个镜头、1 个角色、1 个场景**。
   镜数一多、角色一多是否仍稳定，**不知道**。
   按吸收来的报告，一集里的锁通常是个位数——超过之后本套件没有任何证据。
4. **界面上没有点过**：所有验证都是对路由与提示词的，**不是浏览器操作**。
   侧边栏、工作台面板的实际交互**依然没有真人点过**。
5. **上游 524 无法根治**：只能重试。若要稳定，需要换更快的渠道或模型。
   实测同一提示词、同一模型，成功率在不同时段从 1/4 波动到 4/4。
6. **没有做像素级/人脸相似度度量**，判断依据是**目视特征比对**
   （发型、服装、配饰、工牌、车厢陈设）。这是诚实但**非量化**的结论。
7. **色调一致性未量化**：四张图观感统一，但没有做过色彩直方图比对。
